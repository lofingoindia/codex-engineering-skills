# Security boundaries

Read the relevant boundary, not a mandatory full security audit for every change. Use the [OWASP API Security Top 10](https://api-security.owasp.org/editions/2023/en/0x11-t10/) as a threat-discovery aid, not proof of completeness. It covers object/function/property permissions, authentication, resource and business-flow abuse, SSRF, configuration, inventory, and unsafe upstream consumption.

## Identity and credential lifecycle

Identify callers first: same-origin browser, native app, third-party delegated client, automation, or another workload. Reuse suitable framework sessions or the existing identity provider. A first-party browser app does not automatically need OAuth, JWTs, or an API gateway. API keys identify a client/workload and may convey limited capabilities; do not mistake them for delegated user identity. Use TLS for credentials and sensitive traffic; authenticate workloads as well as end users at their actual trust boundaries.

When OAuth is needed, follow [RFC 9700](https://datatracker.ietf.org/doc/html/rfc9700) and provider-specific guidance: authorization code with PKCE S256, exact redirect validation and transaction binding; avoid implicit issuance of access tokens and do not use the resource-owner password grant. Public clients cannot keep an embedded client secret. Use scopes and resource/audience restriction, but still enforce application permissions. Refresh-token protection, rotation or sender constraints depend on client type and provider capabilities. Do not build an authorization server to add a routine endpoint.

[OpenID Connect](https://openid.net/specs/openid-connect-core-1_0.html) supplies authentication on OAuth. An ID token intended for a client is not an API access token. Validate the correct token type, issuer, audience, signature/allowed algorithm, expiry, and applicable claims with maintained libraries. For opaque tokens, use the provider's supported validation/introspection path. Plan trusted signing-key rotation without accepting arbitrary key URLs from token headers. Decide revocation latency explicitly; a long-lived self-contained token cannot promise immediate revocation without an additional mechanism.

For secrets/API keys, use high entropy, least privilege, tenant binding where applicable, expiry/revocation, rotation overlap, redacted logs, and an appropriate verifier/secret store. Store a one-way verifier when only comparison is required; outbound credentials that must be recovered need protected secret storage. Avoid secrets in URLs or public browser/mobile bundles. Never solve an auth failure by disabling validation.

## Authorization, tenancy, and field exposure

Define who can perform the operation on which object and properties in which tenant/state. Derive authority from verified identity and current membership; a supplied tenant ID is a selector, not proof. Scope reads and writes, joins, relationship assignment, search, exports, cache access, background jobs, status polling, downloads, and batches. Validate both source and destination of moves or cross-object relationships. Scope/role possession alone does not establish object ownership ([OWASP Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)).

Enforce invariants where state is authoritative. Use tenant-scoped queries and appropriate foreign-key/uniqueness constraints or existing row policies. A separate authorization read followed by a global write can race with changes in ownership or membership; choose an atomic predicate/transaction/isolation strategy appropriate to the risk. A UUID is not an access control. Treat an idempotency replay, cursor, signed download, and completed async result as their own access paths; do not let a cache hit bypass current permissions inadvertently.

Allowlist writable fields, enforce function privileges for administrative actions, and explicitly project readable fields. Reject or safely ignore unknown request fields according to the existing contract; neither behavior permits protected-field assignment. Test a valid user acting on another user's object in the same tenant as well as across tenants. Check bulk operations with mixed authorized and unauthorized items and verify the documented atomicity. Prefer uniform safe errors where existence disclosure is sensitive.

## Browser and untrusted-input boundaries

Cookie/ambient-credential mutations need the framework's suitable CSRF defense and secure cookie settings. Choose SameSite behavior for real login, navigation, embedding, and cross-origin flows; Strict can disrupt legitimate entry paths. SameSite alone has deployment-dependent gaps, especially sibling subdomains. CORS controls browser cross-origin access; it is not server-side authorization or a general CSRF defense. For credentialed cross-origin calls, use an explicit allowed origin and correct credential/preflight/cache behavior. Test legitimate origins as well as rejected ones ([CSRF guidance](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html), [REST security](https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html)).

Validate at the boundary and apply context-appropriate safe handling at the sink: parameterized database queries, safe path handling, no shell interpolation of untrusted data, bounded upload/decompression/parser work. Treat upstream API responses as untrusted data too. Limit bodies, nesting, counts, query cost, execution time, and concurrent expensive operations based on the business use. Protect sensitive workflows from automation even when request rate is low. Use tenant/principal limits and fair recovery behavior where appropriate; an IP-only policy can unfairly block shared networks.

User-controlled fetch/webhook destinations require SSRF protection covering parser ambiguities, schemes/ports, IPv4/IPv6, loopback/private/link-local/metadata destinations, DNS changes, and redirects. Prefer known destinations or a proven restricted egress path; validate at connection time, disable redirects or validate every hop, and never forward internal credentials. A URL regex or one DNS lookup is insufficient. Apply time/size limits to fetches ([OWASP SSRF](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html)).

Keep permission-failure and security-event evidence useful without recording tokens, full sensitive bodies, or cross-tenant data. Include affected legacy/debug/API versions in scope when they expose the same operation; fixing one route while leaving a reachable alternate path is not a complete correction.
