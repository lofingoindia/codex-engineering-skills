# Contracts and evolution

Use the affected sections for HTTP/JSON contract work. Protocol conformance and project conventions are different obligations. Sources and publication status are indexed in [sources.md](sources.md).

## Operations and HTTP behavior

Model the consumer's business operation, rather than exposing database tables or forcing every action into generic CRUD. Keep established resource vocabulary, casing, nesting, and identifiers. Resource nouns are a useful default; an explicit command is reasonable when it expresses a real transition better than a fabricated resource. Google's action syntax and Zalando's resource preference are organization conventions, not HTTP requirements ([AIP-136](https://google.aip.dev/136), [Zalando](https://opensource.zalando.com/restful-api-guidelines/)).

Under [HTTP semantics](https://www.rfc-editor.org/rfc/rfc9110.html), safe methods do not request mutations. Idempotent means repeated requests have the same intended effect; status and body need not repeat. PUT expresses replacement; PATCH requires defined patch semantics. Do not depend on GET request bodies across clients/proxies. Use appropriate media types and distinguish 415 unsupported content from 406 unacceptable representation when relevant.

Use success codes for their meaning: 201 for completed creation, identifying the new resource; 202 for accepted, unfinished work; 204 without content. HEAD and 304 also have no response content. For 401 provide the authentication challenge required by the scheme; distinguish insufficient permissions (403) and deliberate existence concealment (404). A failed state precondition commonly produces 412; 409 describes a state conflict. Use 429 for throttling and document retry behavior. Keep a consistent choice for semantic validation errors (often 400 or 422) instead of changing it stylistically. Never hide application failures inside a misleading HTTP success envelope merely for uniformity ([Azure implementation](https://learn.microsoft.com/en-us/azure/architecture/best-practices/api-implementation), [RFC 6585](https://www.rfc-editor.org/rfc/rfc6585.html)).

## Schema and errors

Define what consumers send and receive, independently of what the ORM can bind or serialize. Make required/optional, null, omitted, empty, and default behavior deliberate. Check identifiers and large integers against client numeric limits; represent monetary amounts with an explicit unit/currency and exact arithmetic strategy. Distinguish instants with offsets from dates and local scheduling times. Validate sizes, ranges, enum values, nesting, and business invariants; a schema `format` annotation is not proof that runtime validation occurs.

For partial updates, define absent fields, explicit null, protected fields, arrays, and atomic failure. [JSON Merge Patch](https://www.rfc-editor.org/rfc/rfc7396.html) uses null to remove object members and replaces arrays as units; it cannot express every nullable-domain update conveniently. [JSON Patch](https://www.rfc-editor.org/rfc/rfc6902.html) expresses ordered operations; authorize every affected path, including copy/move sources. Existing domain patches or field masks can be appropriate. [PATCH](https://www.rfc-editor.org/rfc/rfc5789.html) requires atomic application of its patch document; it is not inherently idempotent. Do not implement partial PUT under replacement semantics without recognizing an existing compatibility constraint.

Keep established machine-readable error codes stable. For a new HTTP error contract, consider [RFC 9457 Problem Details](https://www.rfc-editor.org/rfc/rfc9457.html), which supersedes RFC 7807. Use `application/problem+json`, a stable problem identity, and safe actionable detail; any included status agrees with the HTTP status. Consumers should branch on machine fields, not human text. Validation-location and correlation fields are extensions you must define, not standardized required members. Do not leak stack traces, SQL, secrets, or another tenant's existence. Migrate an existing useful error format only with consumer compatibility in mind.

## Lists, queries, and large operations

Choose bounded page size and documented invalid-limit handling using real workload and existing conventions. Small, stable lists may use offset pagination; high churn or expensive deep offsets often favor keyset/cursor pagination. Use a deterministic total order with a unique tie-breaker and a matching index. Changing sort keys or concurrent inserts/deletes can still move records: a cursor alone does not create snapshot consistency.

Bind cursor interpretation to relevant filters/sort/scope; make its representation opaque and validate tampering where it affects safety. Reauthorize every page: a token is not a permission grant. Define expiration and end-of-list behavior, and whether totals are exact, estimated, expensive, or omitted. Adding silent truncation to an existing unpaginated response breaks consumers; plan a compatible endpoint/opt-in or explicit migration ([AIP-158](https://google.aip.dev/158)).

Allowlist query operators, sortable fields, and projections; parameterize values and constrain query cost. Preserve case, time-zone, null-ordering, and search semantics. For bulk work, specify size/cost limits, per-item authorization, order, atomicity versus partial success, and safe item retries. A chosen batch status or envelope is a documented contract, not a universal rule. For large transfers, consider existing streaming or object-storage capabilities with scoped, expiring access instead of buffering huge JSON.

## Contract tooling and change safety

Choose contract-first for coordination with independent consumers or implementation-first with generated contracts when that is the project's sound workflow. Either way, establish a source of truth and detect drift. In OpenAPI, describe auth, limits, errors, pagination, headers, examples, and unique stable operation IDs needed by generated clients. Validate actual requests/responses and the target SDK, not only the document. OAS 3.0 and 3.1+ have different schema/nullability behavior; use the actual dialect. Check supported linters, validators, renderers, and generators before adopting a newer OAS version ([OpenAPI](https://spec.openapis.org/oas/)).

Evaluate source, wire, and semantic compatibility ([AIP-180](https://google.aip.dev/180)). Renames, removed fields, required inputs, tightened validation, changed defaults/order/limits, error changes, and stricter authorization can affect users. Even additive output fields or enum values can break closed parsers, generated SDKs, exhaustive switches, signatures, or snapshots. Test actual supported consumers, especially clients that cannot be upgraded immediately. Security defects may require intentional restriction; identify affected legitimate workflows and a migration instead of preserving a vulnerability.

Keep the existing version strategy if suitable. Path versions are visible and straightforward for routing; negotiated headers/media types require correct cache variation and client support; date/pinned versions add lifecycle cost. None is mandatory for every API. Prefer compatible evolution and introduce parallel versions only when needed. Distinguish API implementation releases, specification versions, and consumer contract versions ([Azure design](https://learn.microsoft.com/en-us/azure/architecture/best-practices/api-design)).

For breaking changes, name affected consumers, migration mechanics, coexistence window, usage evidence, retirement owner, and recovery strategy. Use additive storage changes and mixed-version-safe deployment order where needed; rolling back code may not undo committed data changes. [Deprecation (RFC 9745)](https://www.rfc-editor.org/rfc/rfc9745.html) communicates deprecation, whereas [Sunset (RFC 8594)](https://www.rfc-editor.org/rfc/rfc8594.html) signals expected unavailability. Their wire date syntaxes differ; verify them rather than copying an example. Headers complement migration documentation and consumer communication.
