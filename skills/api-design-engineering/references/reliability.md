# Reliability and performance

Start with the business invariant and failure budget. Select the mechanism that preserves it using the system already present. A cache, queue, lock service, circuit breaker, or distributed transaction is not an automatic prerequisite.

## Duplicate effects and concurrent mutations

For a retryable mutation, define the logical operation identity, key scope (tenant/principal as appropriate plus operation), payload binding, retention window, in-progress behavior, and replay/result semantics. Bound key length/storage. Reject key reuse for a materially different request. Authenticate and authorize replays; a key must not reveal another caller's response. A method being idempotent does not prevent lost updates or provide the same response each time.

Claim the key atomically in shared authoritative storage with a uniqueness constraint or equivalent. Where possible, commit the business mutation and recorded result together. Concurrent duplicates must not both execute. In-memory maps, check-then-insert, and a lock local to one process fail across instances or crashes. Decide what happens after a crash before the effect, after commit before response, during external work, and after retention expires. An external payment cannot be made atomic by a local database transaction: reuse the provider's operation identity/idempotency mechanism and reconcile uncertain outcomes.

[Stripe's documented behavior](https://docs.stripe.com/api/idempotent_requests) is a useful concrete example, not a universal rule: its v1 saves executed responses including 500s; v2 has different completion/recovery semantics. Choose which failures to retain based on the service's actual state machine. Never clear an uncertain result and blindly repeat an irreversible effect. [Idempotency-Key](https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/) is work in progress; verify status and deployed client syntax before claiming standards conformance.

For stock, balances, reservations, and uniqueness, state the invariant first. Protect it with an atomic conditional update, constraint, row lock, compare-and-swap/version predicate, or appropriate isolation. A transaction at default isolation does not make a read-check-write sequence safe. For edit conflicts, strong ETag plus If-Match can expose optimistic concurrency to HTTP clients, but the check and mutation must be atomic. Exercise two competing requests at the shared store, including separate connections/processes where relevant. Retry serialization/deadlock failures only at a safe transaction boundary with a bound; inspect the actual database's semantics ([PostgreSQL isolation example](https://www.postgresql.org/docs/current/transaction-iso.html)).

## Deadlines, retries, and partial failure

Budget end-to-end time across connection setup, DNS/TLS, reading, execution, downstream calls, and cleanup. Verify what the installed client library's timeout actually covers. Propagate remaining deadlines and cancellation where supported, stop unnecessary work, release resources, and reuse bounded connection pools. A disconnected caller does not roll back a committed database write or guarantee that a remote service stopped.

Retry only operations whose repeated effects are safe, for failures likely to be transient. Reuse the same logical-operation key. Coordinate SDK, proxy, application, and job retries to avoid multiplication. Bound attempts and elapsed time, add jittered backoff, respect Retry-After within the deadline, and fail usefully when the budget is exhausted. A received error or timeout can leave a successful remote mutation hidden. Reconciliation or status lookup may be safer than another mutation. Do not blindly retry every 4xx/5xx, and do not add a circuit breaker without checking the existing client's controls and recovery behavior ([AWS Builders' Library](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/)).

Separate optional dependency degradation from required correctness. An unavailable recommendation service might allow a documented reduced response; an unavailable permission check must not silently grant access. Make stale reads, partial responses, and unknown outcomes explicit. Bound queueing/concurrency and reject load before resource exhaustion; make retryable overload distinguishable from permanent failure.

## Async acceptance and cross-system work

Use asynchronous processing when work exceeds request budgets or needs durable retries, not merely because a queue is fashionable. Define operation identity, observable states, result/error, polling/backoff or notification, cancellation semantics, ownership, retention, and recovery after a worker crash. Return accepted only after the promised work is durably recorded. Authorize both submission and status/results; cancellation may be best effort and cannot undo every effect. Repeated submissions should map to the intended logical operation ([AIP-151](https://google.aip.dev/151)).

If a committed database change must reliably publish an event, address the dual-write gap with the existing transactional outbox/CDC or an equivalent recovery mechanism. Outbox commit does not mean exactly-once delivery: dispatch can duplicate, consumers still need atomic deduplication with effects, and per-entity ordering may require explicit sequencing. Avoid network calls while holding database locks when it creates long contention. For cross-service workflows, specify compensation or reconciliation for irreversible partial success; a saga is an option, not a replacement for a local transaction ([AWS outbox guidance](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)).

## Latency, load, and cache correctness

Measure representative latency distributions, throughput, query counts/plans, rows scanned, pool saturation, payload bytes, memory, and dependency time before proposing infrastructure. Check N+1 access and overfetching, indexes matching scoped filters/sorts, unbounded scans/counts, and round trips. A bounded batch or existing projection can be enough; caching does not fix a pathological query or broken authorization. For large payloads, evaluate streaming/compression/object transfers with CPU, memory, proxy, and client constraints.

Apply [HTTP caching](https://www.rfc-editor.org/rfc/rfc9111.html) deliberately. `no-cache` permits storage with revalidation; `no-store` forbids storage by compliant caches; `private` excludes shared caches. Define freshness, validator behavior, mutation invalidation, and stale-serving policy. Private caching can still be inappropriate for sensitive data. Conditional requests save transfers only when validators represent the selected response correctly.

Audit application and CDN/proxy cache keys separately: tenant, principal/permission-sensitive visibility, representation, query, locale, and contract version can matter. Vary covers nominated HTTP request headers; it does not fix a custom cache keyed only by object ID. Review authenticated-response shared caching rules, revocation and permission changes, negative caches, and cross-tenant collisions. Use bounded single-flight/stampede mitigation only where actual hot-key behavior warrants it.

## Production evidence

Reuse instrumentation. Capture route-template latency/error/traffic and saturation, downstream attempts/deadlines, duplicate/replay/conflict outcomes, and async backlog/age/failures relevant to the operation. Correlate logs and traces across owned boundaries without trusting arbitrary external trace baggage. Use low-cardinality route names and scrub sensitive data; do not place raw object/user IDs in metric labels. Respect the instrumentation SDK's supported convention version and distinguish stable from experimental fields ([OpenTelemetry HTTP](https://opentelemetry.io/docs/specs/semconv/http/), [HTTP spans](https://opentelemetry.io/docs/specs/semconv/http/http-spans/)).

For a consequential change, verify what happens under lost responses, duplicate/concurrent calls, crash/restart, slow or failing dependencies, stale caches, and mixed client/server versions. Choose cases that threaten the identified invariant, and inspect state/effect counts. State the workload and evidence behind performance claims. Roll out with observed success/failure criteria and recovery appropriate to the impact; a passing schema validator is insufficient evidence of production readiness.
