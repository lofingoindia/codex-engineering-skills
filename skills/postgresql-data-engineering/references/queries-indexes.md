# Query diagnosis and index engineering

Optimize the observed workload, preserving results, ordering, permissions and durability. Neither fewer SQL statements nor a particular SQL style is inherently faster. A join that multiplies rows or one huge aggregate can cost more than a few bounded indexed requests.

## Collect evidence before changing the plan

Establish representative parameters and tenant/data skew, frequency, rows returned, payload size, pool wait, lock wait and end-to-end latency. Inspect the SQL actually generated by the driver/ORM, including casts and hidden queries. Use existing slow-query evidence or `pg_stat_statements` where available; aggregate totals can hide one tenant's tail latency. Check its reset/collection period and permissions before calling something unused or absent ([statement statistics](https://www.postgresql.org/docs/18/pgstatstatements.html)).

Use plain EXPLAIN first when execution risk is uncertain. EXPLAIN ANALYZE runs the statement and can invoke triggers/functions; a SELECT can also have effects. Prefer disposable representative data for writes/expensive experiments. Transaction rollback does not reverse sequence allocations, external effects, locks already held, WAL/load or work inflicted on others. Do not present a production write-analysis command as harmless because it ends with ROLLBACK.

In a safe environment, inspect actual plans with relevant BUFFERS and other supported options. Compare estimated versus actual rows, loops, filters, join order/algorithms, sort/hash spills, heap fetches, planning and execution time. Costs are planner units, not milliseconds; node timings/rows can be per-loop averages, and parent time includes child work. Buffer reads are not a direct physical-disk latency measurement. State cache state, concurrency, timing overhead and parameter distribution when comparing runs ([EXPLAIN](https://www.postgresql.org/docs/18/using-explain.html)).

## Diagnose before prescribing

- **Bad row estimates:** inspect ANALYZE freshness, skew, correlated predicates, casts, expression/statistics support and suitable extended statistics. An index may not repair wrong cardinality estimates ([planner statistics](https://www.postgresql.org/docs/18/planner-stats.html)).
- **Lock/pool waits:** follow ownership, long transactions and blocking chains; SQL execution may be fast once it runs. Use [transactions/connections](transactions-connections.md) and [operations/recovery](operations-recovery.md).
- **Large work for small output:** inspect predicate placement/indexability, repeated scans, join multiplication, unnecessary sorting, deep offsets and excess selected columns. Validate semantics of NULL, duplicates, outer joins, aggregation and pagination before rewriting.
- **Many small requests:** remove genuinely redundant lookups or batch safely with bounded memory/query size. Do not replace N+1 with an unbounded cross-product or a giant payload.

A sequential scan can be correct for a small table or a large matching fraction. Avoid disabling scan/join methods globally to force a desired plan. Prepared queries can choose custom or generic plans; inspect behavior for materially different parameter values instead of assuming one plan fits every tenant. CTEs are not universally optimization fences on current releases; folding/materialization depends on query/version and can change work or side effects ([PREPARE](https://www.postgresql.org/docs/18/sql-prepare.html), [SELECT](https://www.postgresql.org/docs/18/sql-select.html)).

For pagination, use a deterministic total order with a unique tie-breaker and correct NULL/collation semantics. Keyset pagination can avoid deep-offset work, but mutable sort keys and concurrent changes still affect continuity; it does not automatically produce a snapshot. Avoid exact COUNT on every page when the product needs only continuation, and keep tenant filtering part of the access path.

## Choose an index from the query and write workload

Start with actual predicates, join keys, sort/limit, selectivity, distribution, frequency and existing indexes/constraints. B-tree is often suitable for equality/range/order; GIN for supported containment/search workloads, GiST/SP-GiST for relevant operators, BRIN for large physically correlated data. Choose the operator class and query semantics together; an index label alone does not guarantee support ([CREATE INDEX](https://www.postgresql.org/docs/18/sql-createindex.html)).

For multicolumn B-trees, leading equality and following range/order conditions often guide a useful layout. Do not apply a universal 'most selective column first' rule. PostgreSQL 18 can use skip scans in suitable cases, so 'a missing leading equality makes the index unusable' is also too absolute. Compare real plans and read/write costs on the deployed major version ([multicolumn indexes](https://www.postgresql.org/docs/18/indexes-multicolumn.html)).

Use a partial index when a stable, useful subset matches the workload. The planner must establish that the query implies its predicate; generic parameterized plans may prevent that proof. Expression indexes require the appropriate expression/operator/collation and immutable functions; do not falsely mark a function immutable to make an index possible ([partial indexes](https://www.postgresql.org/docs/18/indexes-partial.html)).

INCLUDE can cover payload columns without making them search keys. Index-only eligibility also requires the relevant access method/columns, and avoiding heap visits depends on visibility-map state. Frequently updated data may still need many heap checks. Wide payloads increase index size/write cost; a covering index is not automatically an improvement ([index-only scans](https://www.postgresql.org/docs/18/indexes-index-only-scans.html)).

Every index consumes storage, cache, write/WAL work, build time and maintenance. Review overlapping indexes and constraint dependencies, but do not drop an index solely because idx_scan is zero: statistics resets, rare critical queries, replicas and uniqueness enforcement matter. Updating indexed fields can reduce HOT opportunities; including every response column can make a high-write workload worse ([HOT](https://www.postgresql.org/docs/18/storage-hot.html)). Use the migration reference for build/removal impact.

## Verify a proportionate improvement

Compare equivalent results and representative before/after plans, latency distributions, buffers/temp work, memory and write overhead. Test common and skewed parameters, meaningful data size and realistic concurrency. A faster empty test table or one warm-cache execution is weak evidence. Report measured benefit and remaining uncertainty; do not extrapolate a large-scale improvement from estimated cost or query count alone.
