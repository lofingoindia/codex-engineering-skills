# Infrastructure, recovery and measured operation

## Select a topology from loss and availability requirements

Record workload roles, peak data/operations, acceptable downtime and loss (RTO/RPO), failure domains, service ownership and recovery capacity. A single small cache can be standalone with deliberate degradation and rebuild. Replicas can improve availability/read capacity but asynchronous reads can be stale. Sentinel provides discovery/automated failover for a non-sharded primary-replica deployment; it does not shard data. Cluster shards slots and adds slot routing, failover and multi-key constraints; it does not fix a single hot key or create stronger consistency. Managed service guarantees, proxy behavior and administrative permissions must be checked separately.

Replication is normally asynchronous. Acknowledged writes can be lost during failover. `WAIT` checks replica acknowledgments for preceding writes on a connection; it is not consensus or a disk-fsync guarantee. `WAITAOF` (7.2+) can wait for configured local/replica AOF synchronization, with its own constraints. Inspect returned counts and timeout; neither command rolls back the earlier write or establishes strong consistency. Maintain appropriate connection ownership and shard routing when using these commands through pools/Cluster.

For Sentinel, distinguish failure-detection quorum from majority authorization for failover. Place voting/replica nodes across relevant failures rather than treating multiple containers on one VPS as host redundancy. Use supported client discovery, protected Sentinel endpoints and correct authentication. In NAT/Docker setups verify announced addresses/ports from actual clients and between nodes. For Cluster, verify seed access, every advertised target and required private node/bus links, slot health, migration and replica topology. Respect the target version's migration semantics; retrying an error is not a proof of safe replay.

## Isolate incompatible workload policies

Disposable cache eviction, stream retention, queue durability, session/revocation state and rate-limit failure behavior can conflict in one instance. Separate instances/services when capacity, durability or eviction requirements genuinely differ. Define what missing session/revocation records mean; eviction or restart must not accidentally grant access or revive a revoked credential. Logical databases do not supply separate memory or failure budgets. `volatile-*` eviction is not per-workload isolation and can run out of eligible expiring keys. `noeviction` rejects memory-growing operations under its limit; it does not provide unlimited safe writes or prevent process/container OOM.

Estimate memory from real key/value cardinality, encoding, metadata/index overhead and working set, not payload bytes alone. Include clients/output buffers, replication backlog, AOF buffers, fragmentation, allocator/RSS differences and fork/copy-on-write peaks. `maxmemory` is not an RSS/container limit; some replication/AOF buffers are excluded from eviction accounting. Leave measured headroom below host/cgroup memory and account for replicas, snapshots, rewrite and resynchronization. Bound large keys, responses, pipelines and per-client queues. More shards do not automatically distribute one hot aggregate; verify placement/skew before changing topology.

## Deploy recoverably

For a VPS/container deployment inspect effective configuration, pinned supported image/build, filesystem ownership, private networking, secrets, restart policy, file descriptors and resource limits. Persistent workloads need correctly mounted, writable storage with known lifetime and disk capacity; a container restart is not a backup. Inspect Linux overcommit, transparent huge pages, swap pressure, CPU throttling and disk/fsync behavior against the actual Redis/kernel guidance. Do not paste universal sysctl values or allocate all RAM to Redis. Make required settings persistent through the existing infrastructure mechanism.

Readiness should reflect role and ability to serve the required operation; liveness should not trigger restart cascades during a dependency incident. Start clients/workers with bounded recovery behavior. For shutdown, stop intake and allow the configured persistence/drain window; do not confuse clean shutdown with recovery from abrupt termination. A persistence-disabled primary auto-restarting empty can propagate empty state to replicas; analyze that configuration before relying on replicas as recovery.

Choose RDB, AOF/fsync policy, both or no persistence from the role's loss tolerance and recovery cost. RDB is a point-in-time snapshot. AOF policy, rewrite behavior, disk errors and crash conditions affect what survives; do not promise zero loss or a universal exact one-second bound. Replication is not backup: corruption, deletion or operator mistakes can propagate.

Keep protected independent backups with retention, compatible artifacts and sufficient restore capacity. For multipart AOF preserve the required manifest/files coherently using version-supported procedures; copying only one arbitrary live file is insufficient. Verify an isolated restore by loading the data, exercising representative application behavior and measuring recoverable point/time against RPO/RTO. Preserve originals before repair tools that can truncate data. Validate topology/client compatibility, persistence format, scripts/Functions, modules, keys and rollout behavior before upgrades. A downgrade may not read newer data formats; define rollback using compatible backups/redeployment, not merely an older image tag.

## Diagnose the application path

Correlate application p95/p99/error rates, client pool/queue wait, Redis command latency and database fallback pressure. Inspect scoped `INFO` memory/stats/commandstats/persistence/replication, evictions/expiry, rejected writes/connections, latency tools and Slow Log. Add stream pending age/backlog, Pub/Sub slow-consumer/reconnect behavior, quota rejection/fallback and slot/skew metrics only for relevant roles. Avoid tenant/key IDs as unbounded metric labels and redact sensitive samples.

Long commands/scripts and large replies can cause head-of-line delays even with I/O threading. Distinguish CPU/command execution, network/pool wait, persistence/fork pauses and OS pressure. Use bounded sampling rather than unrestricted `MONITOR`, `KEYS`, full scans or benchmarks against production. Establish comparable workloads before changing encoding, pipeline size, pool capacity, eviction or topology. A high hit ratio does not establish freshness, isolation or lower total system cost.
