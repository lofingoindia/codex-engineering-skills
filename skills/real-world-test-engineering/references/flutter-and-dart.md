# Flutter and Dart verification

Inspect Flutter/Dart SDK versions, package locks, existing unit/widget/integration tooling, state/navigation setup and platform plugins. Test at the cheapest boundary that exercises the actual behavior; do not replace an existing provider/state system to suit a test example.

Use Dart unit tests for domain rules, serialization, state transitions and adapter behavior that does not require rendering. Return/await Futures and asynchronous matchers; make expected failures fail on unexpected success. Attach error handlers before controlled Futures complete with an error. Unowned late errors can escape a test's useful observation window. Use existing setup/teardown to dispose clients, controllers, subscriptions and state containers, including partial setup failures.

For widgets, mount relevant real providers, navigation and configuration, then act through taps, text, scrolling, keyboard/focus or semantics appropriate to the feature. Use completers or controlled streams to hold and release loading/success/error states. Check the actual visible data, interaction availability and preserved state; request counts can supplement this when duplicate fetching is the requirement. Do not merely assert that a skeleton widget exists while the screen can never complete.

Derive relevant lifecycle sequences: push/pop and return, parameter/tenant changes while a request is pending, rapid submit/retry, or disposal before completion. Keep valid behavior and security boundaries explicit. Assert that stale output does not overwrite the active state and that rejected actions do not mutate the backend contract's state where that boundary is under test. A fake API can establish widget recovery, not actual network/native behavior.

Advance frames/time intentionally with `pump` and the installed testing API. `pumpAndSettle` waits for scheduled frames to cease; an indeterminate progress indicator or recurring animation may never settle. Do not increase its timeout or wrap everything in an async escape hatch to hide incorrect synchronization. Observe the relevant bounded state transition and control the dependency that resolves it. Preserve timer/stream cleanup and meaningful animation/focus behavior without asserting incidental exact frame counts unless timing is the contract.

Widget tests do not prove Android/iOS plugin execution, permission prompts, push/background delivery, secure platform storage, real-device resource pressure or actual performance. Keep plugin/channel doubles for a clearly scoped contract test and identify the platform integration still needed. Use existing supported integration/device facilities for those gaps when authorized; do not claim an emulator/widget pass establishes every supported device/OS combination. Golden tests can protect selected visual baselines, but cannot replace interaction or data-correctness assertions; review changes instead of blindly regenerating them.

Before reporting, distinguish unit, widget, integration, golden, device and performance checks actually run, including the target environment and relevant omissions. Debug-build timing is not a production performance measurement. Sources: [testing levels](https://docs.flutter.dev/testing/overview), [integration testing](https://docs.flutter.dev/testing/integration-tests), [pumpAndSettle semantics](https://api.flutter.dev/flutter/flutter_test/WidgetTester/pumpAndSettle.html), [Dart async tests](https://pub.dev/packages/test).
