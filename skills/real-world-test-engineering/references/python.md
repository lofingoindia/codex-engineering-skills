# Python verification

Inspect the Python version, dependency lock/configuration, pytest/unittest setup, plugins, fixture scopes and CI selection. Reuse existing tooling. Parametrize meaningful equivalence classes/boundaries with clear IDs; create fresh mutable inputs where tests modify them. Avoid large fixtures that silently provide unrelated permissions, data or dependencies and make invalid setup look valid.

Use fixture scope deliberately. A faster session-scoped client/database can leak caches, transactions or auth across cases; function-scoped state is not automatically safe against external workers. Register cleanup after each successful acquisition. If setup raises before a yield fixture reaches `yield`, its after-yield cleanup does not execute; split resource ownership or use appropriate context/finalization so earlier successful work is still released. Do not swallow teardown errors.

Assert returned values, precise error properties and relevant stored/effect state. Ensure exception assertions cover the actual operation rather than setup, and fail on unexpected success. Restore monkeypatches, environment, dependency overrides and global caches. Mock at a boundary appropriate to the claim; an overridden repository or HTTP transport cannot establish real engine or socket behavior. Reuse a real isolated integration fixture when that behavior matters.

Async tests need the project's supported async runner/plugin and event-loop ownership. Inspect discovery mode and fixture loop scopes; verify the coroutine body and assertions actually execute. pytest-asyncio strict/auto modes have different marker/fixture handling, and other projects use AnyIO or another existing approach. Do not install or combine a second plugin blindly. Cancel/await owned tasks, close async clients and avoid reusing loop-bound objects across incompatible fixture scopes. Unawaited-coroutine/thread warnings or background exceptions deserve investigation, not blanket suppression.

Hypothesis is useful where generated domains and properties expose more than examples. Function-scoped pytest fixtures reset once per test invocation, not once per generated example. Arrange per-example reset/cleanup when needed; suppressing the associated health check can leave an unsound test. Preserve minimized failures and replay information with compatible tool versions. A model/property must be independent enough to catch the defect; filtering out most inputs or recomputing expectations with the production helper weakens it. Stateful tests can generate action sequences and check invariants after transitions when a single action test misses the bug.

For flakes, preserve the first failing state and investigate fixture/global leakage, order, timing and shared services. Targeted order/parallel/repetition experiments should test a hypothesis rather than justify “rerun until green.” Distinguish passed behavior, expected failures, skipped tests, infrastructure errors and collection failures. Broaden regression selection only when shared code/contracts or the unresolved risk warrants it.

Sources: [pytest fixtures and safe teardown](https://docs.pytest.org/en/stable/how-to/fixtures.html), [flaky tests](https://docs.pytest.org/en/stable/explanation/flaky.html), [pytest-asyncio ownership/modes](https://pytest-asyncio.readthedocs.io/en/stable/concepts.html), [Hypothesis API/fixture health checks](https://hypothesis.readthedocs.io/en/latest/reference/api.html), [stateful testing](https://hypothesis.readthedocs.io/en/latest/stateful.html).
