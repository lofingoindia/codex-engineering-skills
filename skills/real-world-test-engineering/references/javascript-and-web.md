# JavaScript, TypeScript and web testing

## Node.js and the installed runner

Inspect package scripts, lockfile, runtime version, runner/configuration, module system, setup files and test discovery. Preserve Jest, Vitest, node:test or another sound runner. Features/import paths for timers, mocks, TypeScript and Browser Mode change between releases; do not copy current documentation into an older project without checking compatibility. Transpiling a TypeScript test is not type checking it.

Return/await the asynchronous operation and its assertions, including rejects/resolves matchers and subtests where required. A callback test must signal completion correctly; do not mix incompatible callback/promise completion modes. Make expected-error tests fail on unexpected success. Capture worker/background completion in the test's lifetime instead of relying on a late unhandled rejection to fail the correct test. Inspect runner diagnostics and overall exit status, not only one early PASS line.

Use controlled promise completion for ordering and the runner's supported fake clocks for owned timers. Confirm which timers, dates and microtasks are controlled. Restore mocks/clocks and clean up scheduled work; choose bounded advancement rather than blindly running an endless recurring timer queue. With Testing Library user-event, use the installed version's supported timer-advancement integration instead of disabling realistic event delays to hide a hang.

For service tests, exercise actual parsing, validation, middleware, authorization and error mapping where those are the claim. Inspect headers/body and relevant persistent effects. A handler injected directly can omit real HTTP behavior; use a local server when transport, streaming, abort or connection cleanup matters. Test a timeout after remote commitment differently from a rejection before execution. Runtime worker/thread/shutdown behavior may need a real isolated process rather than a mocked function.

## React and Next.js

Test user-visible behavior through accessible roles/names, labels, interaction and observable state. Use the existing renderer and actual relevant providers/router/query client. Keep test caches and auth/tenant state isolated. Avoid private component state, incidental CSS classes or exact render counts unless that is the specified contract. Strict Mode/development effect behavior is not automatically a production defect; scope request-count assertions to the intended lifecycle and deduplication guarantee.

Control the request at the existing adapter/network boundary. MSW or a current project alternative can retain real client/query behavior while controlling response status, shape, ordering and delays. This is still a simulated provider, not proof of real transport or backend behavior. Surface relevant unexpected API requests so a test cannot quietly reach a real service or miss its handler. Restore handlers and close servers/subscriptions after each owned lifecycle.

Derive the UI sequence from the feature: pending to success, retained data during refresh, genuine empty versus error, failed mutation recovery or stale response after a scope/query change. Trigger the actual interaction, then use awaited find/assertion utilities to observe the outcome. Put the action outside retrying assertions such as `waitFor`; repeated callbacks must not submit the mutation repeatedly. Assert important forbidden output too, such as old-tenant data remaining after a completed switch. Do not require every state for an unrelated small component.

JSDOM/happy-dom simulate browser APIs; they do not establish actual layout, focus behavior, browser integration or native rendering. Browser component tests can close selected gaps without deploying the full system, but still do not prove full routing/proxy/provider behavior. Reuse an existing Browser Mode/Playwright facility when justified rather than automatically migrating a fast component suite. Automated accessibility assertions supplement, not replace, relevant real keyboard/assistive-technology checks.

For Next.js, identify App/Pages Router, server/client execution and the actual framework version. Test domain logic and route/service integration at supported boundaries. Direct function tests may bypass server authorization/session context, caching, serialization or framework request handling. The official testing guidance reviewed on 2026-10-30 still notes incomplete async Server Component support and recommends E2E for those components. Recheck current support; mocking an async Server Component into a client component does not verify the deployed framework. Use targeted framework/browser verification for the remaining boundary, without expanding every utility test into E2E.
